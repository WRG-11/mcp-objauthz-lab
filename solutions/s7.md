# Solution S7 — The Missing Key

## The exploit

Authenticate as Alice (`alice-token`, org *Acme*) and call `note_get_by_query`
with the id of a note you do not own:

```json
{
  "name": "note_get_by_query",
  "arguments": {
    "token": "alice-token",
    "id": "n_globex_1"
  }
}
```

In `LAB_S7=vuln` the server returns Globex's note in full:

```json
{
  "id": "n_globex_1",
  "orgId": "org_globex",
  "ownerId": "u_bob",
  "title": "Globex vendor list",
  "body": "CONFIDENTIAL (Globex only): ..."
}
```

Alice — a member of Acme only — just read a Globex note.

## Why it works

`note_get_by_query` in `src/tools.js` (vuln mode):

```js
guard(async ({ token, id }) => {
  const session = resolveSession(store, token);
  const note =
    modes.s7 === "vuln"
      ? store.findNoteBy({ id })                          // ← tenant key omitted
      : store.findNoteBy({ id, orgId: session.orgId });
  if (!note) notFound(id);
  return ok(note);
}),
```

There is **no `requireOrgAccess` call to be missing** here — and that is the
whole point. `findNoteBy` matches on every key in the filter it is given.
`findNoteBy({ id })` carries only the caller-supplied id, so it matches any
note with that id regardless of org. The authorization was supposed to be the
*second key* in the filter, and it was left out.

This is the shape most real-world object-authz bugs actually take. A production
MCP server fetches from an ORM: `repo.findOneBy({ id, workspaceId })`. The bug
is dropping `workspaceId` from that object — one key inside a `where` clause,
with nothing else visibly wrong. It is exactly **CVE-2026-54052** (n8n, CVSS
9.6): a table fetched by a sequential id with the tenant column left out of the
query, exposing every tenant's stored secrets. An S1-style "find the missing
guard call" review walks straight past it, because the guard is data, not code.

## The fix

`LAB_S7=fixed` binds the tenant key into the same query:

```js
const note = store.findNoteBy({ id, orgId: session.orgId });
```

Now a cross-org id resolves to nothing and the tool returns "not found." The
fix adds no new check — it completes the one that was always supposed to be
there. When you review a query-scoped codebase, the audit is not "is there a
guard call?" but "does every fetch-by-id carry the tenant key?"

## How real servers get this right

The four production MCP servers this lab's detection notes were validated
against all defend the same way, at the query:

- **Flowise** — `Credential.findOneBy({ id, workspaceId })`, and the
  `workspaceId` is taken from `req.user.activeWorkspaceId` (the session), never
  from the request body.
- **activepieces** — `recordRepo.findOne({ where: { id, projectId, tableId } })`,
  with `projectId` from the server-trusted MCP session.
- **n8n** — access flows through a sharing model scoped to the caller's
  projects; privileged instance-level fetches are gated by a global-scope check.
- **Directus** — every item fetch carries the caller's `accountability`, and
  the permission engine enforces it per-collection.

The through-line: the tenant identity comes from the authenticated session, and
it is bound into the query — not asserted in a separate line afterward.
