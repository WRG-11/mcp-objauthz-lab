# Solution S8 — The Path You Wrote

## The exploit

Authenticate as Alice (`alice-token`, org *Acme*) and issue a `resources/read`
call for the URI, substituting Globex's note id and Globex's org id into the
template yourself:

```json
{
  "method": "resources/read",
  "params": {
    "uri": "note://alice-token/org_globex/n_globex_1"
  }
}
```

In `LAB_S8=vuln` the server returns Globex's note in full:

```json
{
  "id": "n_globex_1",
  "orgId": "org_globex",
  "ownerId": "u_bob",
  "title": "Globex roadmap",
  "body": "CONFIDENTIAL (Globex only): the next-quarter roadmap."
}
```

Alice — a member of Acme only — just read a Globex note, without ever calling
a tool.

## Why it works

The `note` resource template in `src/tools.js` (vuln mode):

```js
async (uri, { token, orgId, noteId }) => {
  const session = resolveSession(store, token);
  const scope = modes.s8 === "vuln" ? orgId : session.orgId;
  const note = store.findNoteBy({ id: noteId, orgId: scope });
  ...
}
```

`{token}` is the caller's identity — server-trusted, resolved through
`resolveSession` exactly like every tool in this lab. `{orgId}` looks like the
same kind of thing: another segment of the URI the caller supplied. It is not.
It is the *scope*, and in vuln mode the handler binds `store.findNoteBy`'s
tenant key straight to it. Whoever writes the URI chooses whose data the read
resolves against — the identity check and the authorization check are reading
from two different sources, and only one of them is trustworthy.

## Why this is MCP-specific, not just "the same bug again"

`resources/*` is a distinct primitive from `tools/*` in the MCP spec: separate
registration (`registerResource` + `ResourceTemplate` vs. `registerTool`),
separate handler shape (`(uri, variables)` vs. a single args object), separate
client-side call (`resources/read` vs. `tools/call`). A review that greps
`registerTool` calls — which is every scenario S1-S7 in this lab — walks
straight past this resource and never sees it.

There is a second reason it is quieter than S1-S7. Many MCP hosts prompt the
user (or the calling agent's policy layer) for approval before a tool call,
but read a resource with a lighter touch or none at all — resources are
commonly treated as inert reference material, not an action. The exact same
authorization bug is harder to notice happening and, in an agentic pipeline,
easier for a manipulated or careless model to trigger without a human in the
loop.

## The fix

`LAB_S8=fixed` ignores the `orgId` path segment entirely and uses the
session's own org instead:

```js
const scope = session.orgId;
```

The URI still carries three variables — the fix does not remove `{orgId}`
from the template, because doing so would be a breaking change to the
resource's shape (same convention as S2/S4/S6 ignoring an argument rather
than deleting it). It is simply never trusted as authorization. Now a
cross-org id resolves to "not found," and Alice can still read her own notes
through `note://alice-token/org_acme/n_acme_1` without any change.

## How real servers get this right

The tenant identity has to come from something the caller cannot rewrite. For
a per-call bearer token model like this lab's, that means: resolve the
session from the token first, and use *that* org — never a path segment,
query parameter, or any other value the URI template exposes back to the
caller. The same principle S2, S4, S6, and S7 teach on the tools surface
applies unchanged here; only the primitive carrying the untrusted value is
different.
