# Solution S10 — The Header the Gateway Trusts

**Class:** CWE-639 / CWE-290 — forwarded-header-as-scope (transport surface)

## The bug

`note_get_scoped` derives the authorization scope from a request **header**:

```js
guard(async ({ token }, extra) => {
  const session = resolveSession(store, token);
  // S10 vuln: trust the client-supplied X-Org-Id header as the scope.
  const headerOrg = extra?.requestInfo?.headers?.["x-org-id"];
  const effectiveOrgId =
    modes.s10 === "vuln" && headerOrg ? headerOrg : session.orgId;
  return ok(store.listNotesByOrg(effectiveOrgId));
});
```

Over the streamable-HTTP transport the SDK hands every tool call the request's
headers in `extra.requestInfo.headers`. A server deployed behind a gateway is
tempted to treat an identity/routing header — `X-Org-Id` here — as
authoritative, because "the gateway sets it." But **the gateway is not the
only thing that can send it.** A client talking to the server directly sets
whatever headers it likes; the header is client-controlled input wearing the
costume of infrastructure. This is the same defect as S2 (scope-as-param), one
layer down: the scope now rides in a header instead of a tool argument.

It is the well-known real-world class of *trusting `X-Forwarded-For` (or any
`X-*` identity header) for a security decision*. The IP-scoping variant —
trusting `X-Forwarded-For` for rate-limiting or an IP allowlist — is the same
bug and the same fix.

## Exploit

```
# Authenticate as Alice (org_acme), but send X-Org-Id: org_globex.
POST http://127.0.0.1:3010/mcp
X-Org-Id: org_globex
{ "method": "tools/call",
  "params": { "name": "note_get_scoped", "arguments": { "token": "alice-token" } } }

→ [ { "id": "n_globex_1", "orgId": "org_globex", "title": "Globex roadmap", ... } ]
```

Alice reads Globex's confidential notes with nothing but one extra header.

## Why stdio hides it

Run the *stdio* server (`src/server.js`) and the same tool is safe: stdio
carries no request headers, so `extra.requestInfo` is undefined and the tool
falls back to `session.orgId`. The bug only exists in the HTTP deployment —
which is exactly why a review that only exercises the local stdio server never
sees it, and why S10 ships its own `src/http-server.js`.

## The fix

Never read authorization scope from a request header. Derive it from the
server-trusted session:

```js
// S10 fixed: ignore the header; always use session.orgId.
const effectiveOrgId = session.orgId;
return ok(store.listNotesByOrg(effectiveOrgId));
```

If a gateway genuinely needs to pass identity, it must do so through a channel
the server can *authenticate* (a signed token the server verifies, mTLS client
identity, a trusted-network segment that strips inbound `X-*` headers) — never
a plain header the untrusted client can also set.

## Detection

The `mcp-authz-scope-from-request-header` Semgrep rule flags a scope-shaped
header (`X-Org-Id`, `X-Forwarded-For`, ...) read from `extra.requestInfo.headers`
(or a FastMCP `get_http_headers()` in the `-py` sibling). It keys on the header
*name*, so a non-scope header such as `X-Request-Id` read for logging stays
silent.
