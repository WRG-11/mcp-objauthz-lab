# Solution S11 — The Quota the Gateway Trusts

**Class:** CWE-639 / CWE-290 — X-Forwarded-For quota/rate-limit bypass (transport surface)

## The bug

`note_create_limited` derives the quota key from a request **header**:

```js
guard(async ({ token, title, body }, extra) => {
  const session = resolveSession(store, token);
  // S11 vuln: quota keyed on X-Forwarded-For header (client-controlled).
  const quotaKey =
    modes.s11 === "vuln"
      ? extra?.requestInfo?.headers?.["x-forwarded-for"] ?? session.orgId
      : session.userId;
  const currentCount = store.getQuotaCount(quotaKey);
  if (currentCount >= 3) {
    return fail(`Quota exceeded for ${quotaKey}. Maximum 3 notes per client.`);
  }
  const note = store.createNote({
    orgId: session.orgId,
    ownerId: session.userId,
    title,
    body,
  });
  store.incrementQuota(quotaKey);
  return ok(note);
});
```

Over the streamable-HTTP transport the SDK hands every tool call the request's headers in `extra.requestInfo.headers`. A server deployed behind a gateway is tempted to use an identity/routing header — `X-Forwarded-For` here — as the client identity for rate limiting or quotas, because "the gateway sets it." But **the gateway is not the only thing that can send it.** A client talking to the server directly sets whatever headers it likes; the header is client-controlled input wearing the costume of infrastructure.

This is the **quota/rate-limit sibling of S10**. S10 trusts `X-Org-Id` for *authorization scope* (whose data to return). S11 trusts `X-Forwarded-For` for *quota identity* (which client's counter to check). Both are the same defect: a client-controlled header used for a security decision (authorization scope vs. rate-limit identity). The fix is the same: derive the decision from the server-trusted session.

## Exploit

```
# Authenticate as Alice (org_acme), quota exhausted after 3 notes.
# Send X-Forwarded-For: 1.2.3.4 — a new "client identity" — to reset the quota.
POST http://127.0.0.1:3010/mcp
X-Forwarded-For: 1.2.3.4
{ "method": "tools/call",
  "params": { "name": "note_create_limited", "arguments": { "token": "alice-token", "title": "note 4" } } }

→ Note created! Quota counter for "1.2.3.4" is now 1.
```

Repeat with different XFF values to create unlimited notes. The server thinks each request is from a different client.

## Why stdio hides it

Run the *stdio* server (`src/server.js`) and the same tool is safe: stdio carries no request headers, so `extra.requestInfo` is undefined and the tool falls back to `session.userId` (the fixed behavior). The bug only exists in the HTTP deployment — which is exactly why a review that only exercises the local stdio server never sees it, and why S11 ships on `src/http-server.js` like S10.

## The fix

Never read rate-limit/quota identity from a request header. Derive it from the server-trusted session:

```js
// S11 fixed: quota keyed on session (server-trusted).
const quotaKey = session.userId;
const currentCount = store.getQuotaCount(quotaKey);
if (currentCount >= 3) {
  return fail(`Quota exceeded for ${quotaKey}. Maximum 3 notes per client.`);
}
```

If a gateway genuinely needs to pass client identity for rate limiting, it must do so through a channel the server can *authenticate* (a signed token the server verifies, mTLS client identity, a trusted-network segment that strips inbound `X-*` headers) — never a plain header the untrusted client can also set.

## Detection

The `mcp-ratelimit-scope-from-forwarded-header` Semgrep rule flags a quota/rate-limit identity header (`X-Forwarded-For`, `X-Real-IP`, `X-Client-IP`, ...) read from `extra.requestInfo.headers` and used as the key for a quota/rate-limit counter. It keys on the header *name* and the *usage pattern* (passed to a quota/rate-limit store call), so a non-quota header read for logging stays silent — the two-way canary.
