# Solution S13 — The Token That Lies

**Class:** CWE-639 / CWE-290 — JWT/token scope confusion (scope claim in token vs actual permissions mismatch)

## The bug

`note_get_by_token_scope` derives the authorization scope from a **scope claim
inside the token** (or a parameter mirroring it):

```js
guard(async ({ token, scope }) => {
  const session = resolveSession(store, token);
  // S13 vuln: trust the caller-supplied scope claim (from token's aud/scope) as the authorization scope.
  // S13 fixed: always use session.orgId (server-trusted); ignore token's scope claim.
  const effectiveOrgId =
    modes.s13 === "vuln" && scope ? scope : session.orgId;
  return ok(store.listNotesByOrg(effectiveOrgId);
});
```

The tool accepts a `scope` parameter that represents what a token's `aud`
(audience) or `scope` claim might carry. In vuln mode the server trusts this
claim and uses it to select which organization's notes to return. But the
token's scope claim is **client-controlled input** — any caller can present a
token with an inflated scope claim (or simply pass a `scope` parameter in this
simplified model) that the server trusts without re-verifying against the
identity provider or session.

This is the MCP-specific variant of **JWT scope confusion**: the token
authenticates *who you are* (Alice, org Acme), but the server then trusts a
claim inside that token (or a derived parameter) about *what you may access*
(scope=org_globex). The token's scope claim may not match the caller's actual
permissions — it may be stale, misconfigured, or deliberately inflated by a
malicious client.

## Exploit

```json
{
  "name": "note_get_by_token_scope",
  "arguments": {
    "token": "alice-token",
    "scope": "org_globex"
  }
}
```

→ Returns Globex's notes:
```json
[
  {
    "id": "n_globex_1",
    "orgId": "org_globex",
    "ownerId": "u_bob",
    "title": "Globex roadmap",
    "body": "CONFIDENTIAL (Globex only): the next-quarter roadmap."
  },
  ...
]
```

Alice reads Globex's confidential notes with nothing but a spoofed scope
parameter (mirroring a token with an inflated `aud`/`scope` claim).

## Why this is MCP-specific

In MCP, every tool call carries a token. The server resolves the token to a
session (`resolveSession(token)`) which contains the server-trusted identity
and permissions. The bug is when the server **ignores the resolved session's
scope** and instead trusts a scope/aud claim carried in the token itself (or a
parameter derived from it). This is exactly the same defect as S2 (scope-as-param)
and S10 (forwarded-header-as-scope), but the scope now rides in a **token
claim** instead of a tool argument or HTTP header.

The token is presented per-call, and in an agentic loop the model's context
may contain tokens from multiple sources. A malicious or misconfigured client
can present a token with an inflated scope claim that the server trusts without
re-verifying — the authority must live in the server-resolved session, not in
the token's self-asserted claims.

## The fix

Never trust a token's scope/aud claim for authorization decisions. Derive the
scope from the server-trusted session:

```js
// S13 fixed: ignore the token's scope claim; always use session.orgId.
const effectiveOrgId = session.orgId;
return ok(store.listNotesByOrg(effectiveOrgId));
```

If an identity provider genuinely needs to convey scope, it must do so through
a channel the server can *verify* (a signed token the server validates against
a trusted JWKS, mTLS client identity, a trusted network segment) — never a
claim the untrusted client can also set or inflate.

## Detection

The `mcp-client-supplied-scope-overrides-session` Semgrep rule (S2's rule)
already flags this pattern when the scope parameter name matches
`org_id`/`tenant_id`/`project_id`/... The scope parameter here is named
`scope` which is not in the default list — this is a documented limitation of
name-based detection. Adapt the rule's `metavariable-regex` to include `scope`
and `aud` for your codebase's vocabulary.
