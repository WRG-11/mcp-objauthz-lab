# Solution S12 — The Batch That Leaks

## The exploit

Authenticate as Alice (`alice-token`, org *Acme*) and call `note_batch_resolve`
with a batch containing both your own note and a Globex note:

```json
{
  "name": "note_batch_resolve",
  "arguments": {
    "token": "alice-token",
    "ids": ["n_acme_1", "n_globex_1"]
  }
}
```

In `LAB_S12=vuln` the server returns both notes in full:

```json
[
  {
    "id": "n_acme_1",
    "orgId": "org_acme",
    "ownerId": "u_alice",
    "title": "Acme acquisition memo",
    "body": "CONFIDENTIAL (Acme only): terms for the pending acquisition."
  },
  {
    "id": "n_globex_1",
    "orgId": "org_globex",
    "ownerId": "u_bob",
    "title": "Globex roadmap",
    "body": "CONFIDENTIAL (Globex only): the next-quarter roadmap."
  }
]
```

Alice — a member of Acme only — just read a Globex note by including it in a
batch alongside her own note.

## Why it works

`note_batch_resolve` in `src/tools.js` (vuln mode):

```js
guard(async ({ token, ids }) => {
  const session = resolveSession(store, token);
  const resolved = ids.map((id) => store.getNote(id)).filter(Boolean);
  // S12 vuln: return all resolved notes with no per-item org check.
  // S12 fixed: filter each resolved note to caller's org before returning.
  const result =
    modes.s12 === "vuln"
      ? resolved
      : resolved.filter((n) => n.orgId === session.orgId);
  return ok(result);
}),
```

The batch endpoint resolves every id in the list directly from storage
(`store.getNote(id)`) and returns all resolved notes without checking whether
each one belongs to the caller's org. This is the **batch equivalent of the
list→get asymmetry** (S3) — the same bug at batch scale. S3's `note_batch_get`
had a correctly-scoped `note_list` sibling; here the batch endpoint stands
alone, so the missing per-item check is the only authorization.

This pattern is extremely common in real MCP servers: a "resolve many" endpoint
that takes an array of ids and returns the resolved objects, but forgets to
filter each one to the caller's tenant. The fix is the same as S3 — filter the
resolved items to `session.orgId` before returning.

## The fix

`LAB_S12=fixed` filters each resolved note to the caller's org:

```js
const result = resolved.filter((n) => n.orgId === session.orgId);
```

Now a cross-org id in the batch resolves to a note that is silently dropped.
The fix adds no new check — it completes the authorization that should have been
applied to each item in the batch.

## How real servers get this right

The same production MCP servers from S7 defend this the same way, at the batch
resolution:

- **Flowise** — batch credential resolution filters each result to
  `req.user.activeWorkspaceId`.
- **activepieces** — batch record fetch uses `recordRepo.findByIds(ids)` then
  `.filter(r => r.projectId === session.projectId)`.
- **n8n** — batch operations go through the sharing model; each resolved item
  is checked against the caller's project membership.
- **Directus** — batch read (`items.read` with multiple ids) enforces
  `accountability` per-item through the permission engine.

The through-line: every item in a batch must be individually scoped to the
caller's tenant. A batch endpoint that skips per-item checks is a BOLA waiting
to happen.
