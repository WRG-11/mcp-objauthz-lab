# Challenge S13 — The Token That Lies

**Difficulty:** Intermediate
**Class:** CWE-639 / CWE-290 — JWT/token scope confusion (scope/aud claim in token vs actual permissions mismatch)
**Tool under test:** `note_get_by_token_scope`

```bash

```

## Your mission

You are **Alice** (`alice-token`, org *Acme*). The lab exposes
`note_get_by_token_scope`, which returns notes for the organization indicated
by the token's scope claim. The tool description says it *"uses the token's
aud/scope claim to determine which organization's notes to return."*

You are not a member of *Globex*. You have no Globex token, no membership —
only `alice-token`. But the tool accepts an optional `scope` parameter that
mirrors what a token's `aud` (audience) or `scope` claim might carry.

Call `note_get_by_token_scope` with your `alice-token` and a `scope` parameter
set to `org_globex`. In vuln mode the server trusts the scope claim and returns
Globex's notes.

## What to look for

- Which value does the tool use to decide *whose* notes to return — something
  the server derived from your token (the session), or something the token
  *claims* (the scope/aud parameter)?
- The token authenticates *who you are*; the session determines *what you may
  access*. When these diverge, you have scope confusion.
- This is the MCP-specific variant of JWT scope confusion: the token is
  presented per-call, and a malicious client can present a token with an
  inflated scope claim that the server trusts without re-verifying against the
  identity provider.

## Success criterion

The exploit succeeds when a request you authenticate as **Alice** returns a
note whose `orgId` is `org_globex` (e.g., `n_globex_1`, "Globex roadmap").

## Verify the fix

Restart with `LAB_S13=fixed node src/server.js` and repeat: the same spoofed
scope parameter is now ignored, and you only ever see *Acme* notes.
