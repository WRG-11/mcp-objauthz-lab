# Challenge S9 — The Grant You Can Edit

**Difficulty:** Intermediate
**Class:** CWE-639 — authz-from-client-round-tripped-value (tool-chaining surface)
**Tools under test:** `note_share_prepare`, `note_share_redeem`

## Setup

```bash
npm install

# Only S9 is left vulnerable; the rest default to "vuln" when unset.
LAB_S9=vuln LAB_S1=fixed LAB_S2=fixed LAB_S3=fixed LAB_S4=fixed LAB_S5=fixed LAB_S6=fixed LAB_S7=fixed LAB_S8=fixed LAB_S10=fixed LAB_S11=fixed node src/server.js
```

## Your mission

You are **Alice** (`alice-token`, org *Acme*). The lab exposes a two-step
sharing flow across two tools:

- `note_share_prepare` mints an opaque **grant** string for one of your own
  notes. It is correctly authorized — you can only prepare a grant for a note
  your session can already access.
- `note_share_redeem` takes a grant and returns the note it names.

You want to read Globex's note `n_globex_1`. You are not a member of *Globex*
— no Globex token, no membership, nothing. You only have `alice-token`.

Call `note_share_prepare` once, look closely at what the grant actually is,
and figure out what it would take to redeem a *different* note than the one
you prepared it for.

## Constraints

- Token: `alice-token` only.
- `LAB_S9=vuln` must remain set.
- You may call `note_share_prepare` and `note_share_redeem` as many times as
  you like, but you must never authenticate as anyone other than Alice.

## Verification

The exploit succeeds when a `note_share_redeem` call authenticated as Alice
returns a note with `"orgId": "org_globex"`, even though `note_share_prepare`
was only ever called for Alice's own Acme note.
