# Challenge S7 — The Missing Key

**Difficulty:** Intermediate
**Class:** CWE-639 — Unscoped query (tenant key omitted from the filter)
**Tool under test:** `note_get_by_query`

## Setup

```bash
npm install

# Only S7 is left vulnerable; the rest default to "vuln" when unset.
LAB_S7=vuln LAB_S1=fixed LAB_S2=fixed LAB_S3=fixed LAB_S4=fixed LAB_S5=fixed LAB_S6=fixed LAB_S8=fixed LAB_S9=fixed LAB_S10=fixed LAB_S11=fixed node src/server.js
```

## Your mission

You are **Alice** (`alice-token`, org *Acme*). The lab exposes
`note_get_by_query`, which resolves a single note by id through a filtered
store query — the shape a real MCP server uses when it fetches from an ORM
(`repo.findOneBy({ id, workspaceId })`).

You want to read Globex's note `n_globex_1`. You are not a member of *Globex* —
no Globex token, no membership, nothing.

Your goal: read the full contents of `n_globex_1` using only your own
`alice-token`.

Unlike S1, there is no `requireOrgAccess` call anywhere in this tool to "find
missing." The authorization lives entirely inside the query filter. Look at
what the filter carries — and what it does not.

## Constraints

- Token: `alice-token` only.
- `LAB_S7=vuln` must remain set.
- One `note_get_by_query` call is enough.

## Verification

The exploit succeeds when the note returned by `note_get_by_query` has
`"orgId": "org_globex"`, even though the call was authenticated as Alice
(org Acme).
