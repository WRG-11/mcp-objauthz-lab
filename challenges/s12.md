# Challenge S12 — The Batch That Leaks

**Difficulty:** Intermediate
**Class:** CWE-639 / CWE-862 — Batch/bulk endpoint BOLA (multi-object endpoint without per-item tenant filter)
**Tool under test:** `note_batch_resolve`

## Setup

```bash
npm install

# Only S12 is left vulnerable; the rest default to "vuln" when unset.
LAB_S12=vuln LAB_S1=fixed LAB_S2=fixed LAB_S3=fixed LAB_S4=fixed LAB_S5=fixed LAB_S6=fixed LAB_S7=fixed LAB_S8=fixed LAB_S9=fixed LAB_S10=fixed LAB_S11=fixed LAB_S13=fixed node src/server.js
```

## Your mission

You are **Alice** (`alice-token`, org *Acme*). The lab exposes
`note_batch_resolve`, which resolves multiple notes by id in a single batch call —
the shape a real MCP server uses when it fetches a list of objects by their ids
(`store.getNote(id)` for each id in the batch).

You want to read Globex's note `n_globex_1`. You are not a member of *Globex* —
no Globex token, no membership, nothing. But you know the note ids are
guessable (`n_acme_1`, `n_globex_1`, `n_initech_1`, ...).

Your goal: read the full contents of `n_globex_1` using only your own
`alice-token`, by including it in a batch request alongside one of your own
notes.

Unlike S3 (list→get asymmetry), this tool is a *single* batch endpoint — there
is no separate "list" tool to compare against. The bug is that the batch
endpoint simply resolves every id without checking whether each resolved object
belongs to the caller's org.

## Constraints

- Token: `alice-token` only.
- `LAB_S12=vuln` must remain set.
- One `note_batch_resolve` call with a mixed batch is enough.

## Verification

The exploit succeeds when the batch returned by `note_batch_resolve` includes
a note with `"orgId": "org_globex"`, even though the call was authenticated as
Alice (org Acme).
